# النسخ الاحتياطي، الفشل الجزئي والرجوع

## قبل المخطط والقوائم

على ملف غير فارغ، RB_setup وRB_refreshValidation يحتاجان نسخة تنطبق على الحالة الحالية. RB_createBackup ينشئ نسخة Spreadsheet كاملة، ثم يقارن بصمة قيم الخلايا، الصيغ (لا نتائج الصيغ المتقلبة)، أسماء التبويبات، timezone، قواعد validation الموجودة داخل نطاق البيانات وNamed Ranges. لا يطبع المحتوى أو البريد في logs تقنية. سجل Properties يحمل ID وبصمة وتاريخ التحقق.

المقارنة المحلية لا تثبت أن Google نفّذ نسخًا أو أن كل sharing/protection أو validation خارج used range نُسخ؛ ذلك يحتاج فحص النسخة في Google. لا تشمل البصمة كل ألوان/أبعاد/صلاحيات الملف أو مصدر المشروع/triggers/Properties. احفظي مصدر المشروع والـdeployment/version منفصلًا. إذا تغيرت البيانات بعد أخذ النسخة أو فشل التطابق، يُرفض التجهيز ويجب إنشاء نسخة جديدة مع إيقاف التعديلات مؤقتًا.

التجهيز لا يمسح سجلات، لكنه يضيف أعمدة metadata وجداول إعدادات وينسّق النطاقات ويضع filters. Google Sheets لا يقدم transaction تشمل كل ذلك: فشل setup في المنتصف قد يترك بعض التغييرات المضافة، ولذلك نحتفظ بالنسخة أولًا ونراجع الخطأ قبل الإعادة أو الرجوع.

## كتابة سجلات التشغيل

تُتحقق المدخلات قبل حجز عملية. كل عملية تستخدم ScriptLock ثم:

1. حفظ Request ID والعملية وEntity ID وبصمة payload والحالة PENDING؛ لا تُنسخ الملاحظات أو بيانات العميلات إلى سجل الطلبات.
2. كتابة صف السجل الأساسي مرة واحدة مع Last Request ID.
3. إضافة نشاط واحد مرتبط بـRequest ID.
4. تعليم الطلب DONE، ثم تحديث dashboard كبيانات مشتقة.

هذا sequencing للتعافي، وليس ACID transaction من Google. إذا فشل بعد بدء التسلسل، الخطأ RB_PENDING يوضح أن السجل قد يكون حُفظ. أعيدي **نفس** requestId وpayload بدل إنشاء سجل جديد. الواجهة تحتفظ بالطلب أثناء فتحها وتعطي زر إعادة نفس الطلب؛ تغيير payload بنفس ID يُرفض. أي طلب مختلف يُمنع أثناء وجود PENDING حتى لا تُطمس أدلة الاستعادة.

إذا أُغلقت الواجهة وفُقد payload، يمكن للمديرة تشغيل `RB_recoverPending('Request-ID')` من المحرر بعد مراجعة سجل الطلبات. يعيد إتمام audit وحالة الطلب **فقط إذا** كان صف Entity ID يحمل نفس Last Request ID. لا يخمّن نجاح كتابة غائبة، ولا يحذف PENDING ولا يغيّر البيانات لإظهار نجاح زائف. العملية الإدارية نفسها تسجّل حدث استعادة. إذا لم توجد أدلة كافية، احتفظي بالنسخ وتوقفي عن الكتابة؛ قارني المصدر مع النسخة بمساعدة المسؤول، أو أعيدي الطلب الأصلي. لا تحرري سجل الطلبات أو علامات metadata يدويًا لتجاوز المنع.

معرفات الطلبات تمنع التكرار على مستوى المشروع نفسه. لا يشمل ScriptLock تحرير الخلايا يدويًا أو Apps Script آخر. لا تشغّلي مشروعين يكتبان نفس المصدر ولا تعتمدي على lock لحماية paste يدوي. تحققي من الطلبات والبيانات بعد انقطاع الشبكة قبل إعادة إدخال سجل.

## الرجوع

1. أوقفي استخدام Web App/Sidebar وكتابات الموظفات وأي تكامل خارجي على الملف.
2. احتفظي بالملف المتأثر والنسخة الاحتياطية ولا تحذفي أيًا منهما. وثّقي IDs وتواريخ النسخ في سجل خاص، لا تنشري بيانات عميلات.
3. افتحي النسخة المتحقق منها، وافحصي عدد الصفوف والأعمدة وقيمًا وصيغًا وقوائم مختارة في Google. قارني السجلات التي أضيفت بعد النسخ قبل أي عكس؛ لا تستبدلي ملف الإنتاج بنسخة قديمة بلا مراجعة وموافقة.
4. استرجاع source/deployment إلى version سابق مستقل عن استرجاع بيانات Spreadsheet. لا تعتبرين نسخ الكود rollback للمدفوعات أو السجلات.
5. تبديل Spreadsheet ID أو نسخ نطاقات إلى الإنتاج إجراء يدوي منفصل يحتاج موافقة بعد المراجعة. RB_bindSpreadsheet يرفض تبديل الربط تلقائيًا. عند فتح copy أو إعادة ربط مشروع اختبار، راجعي Properties والتبويب النشط أولًا كي لا يتجه copy إلى الإنتاج.
6. أعيدي اختبارات القراءة والكتابة المعزولة والصلاحيات قبل فتح التشغيل. لا توجد دالة مسح/استعادة أو حذف تلقائي في الحزمة.

لم يُنفَّذ backup أو restore على Google في هذه الجلسة. اختبارات الاختلاف/رفض backup قديم محلية ومحاكية فقط.
