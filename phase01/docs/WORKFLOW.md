# رحلة التشغيل، القوائم وحدود المرحلة

## رحلة موثقة

1. **استفسار → ملف عميلة:** من Sidebar أو Web App، أضيفي اسمًا حقيقيًا وموبايلًا إن توفر وتاريخ الفرح الأصلي والمكان والمصدر والفستان المهتمة به والخدمة والموديل والموظفة والملاحظات. الاسم مطلوب؛ رقم الهاتف اختياري لكنه يُفحص عند إدخاله. يتولد ID ثابت وتاريخ إنشاء وآخر تعديل. لا تُضاف بيانات seed للشيت.
2. **تكرار الهاتف:** يظهر Customer ID الموجود دون دمج. افتحي الملف أولًا. إذا كانت عميلة مختلفة بالفعل تشترك في نفس الرقم، التأكيد الصريح ينشئ ID آخر؛ لا يغيّر السجل القديم. لا يُعاد فحص أرقام تاريخية غير متغيرة بطريقة تمنع تعديل ملاحظة أخرى، ولا تُصحّح أرقام ناقصة بالتخمين.
3. **تأهيل الاستفسار:** افتحي ملف العميلة وعدّلي الحالة والاهتمام والمصدر والمسؤولة والملاحظات. يبقى ID وتاريخ الإضافة كما هما. غير المعروض من أعمدة أصلية يبقى محفوظًا، بما فيه الصيغ والقيم النصية التي تشبه الصيغ.
4. **الفستان المهتمة به:** كود الفستان ليس عقدًا أو حجز مخزون. لا يوجد Dress Catalog مؤكَّد أو سعر/مقاس/توافر في الملفات المتاحة. يمكن إدخال كود موثَّق، وقائمة الموديلات تُستخرج من المصدر أو تُضبط يدويًا. A-Line/Mermaid/Princess/Satin أمثلة تاريخية وليست inventory مُنشأ.
5. **المواعيد:** اختاري Customer ID موجودًا، تاريخ ISO ووقتًا وموظفة ونوع الموعد والحالة والملاحظات. يمكن حجز زيارات متعددة للعميلة. يتوقف الحجز عند نفس اليوم ووقت البداية للموظفة أو العميلة؛ الملغي لا يحجز الفترة. لا توجد قاعدة مدة جلسة أو buffers مؤكدة، لذلك لا ندّعي منع كل تداخل زمني. تعديل موعد يحتفظ بمعرّفه وتاريخ إنشائه.
6. **المتابعات:** اربطي المهمة بالعميلة والموظفة والاستحقاق. تعرض الواجهة اليوم، المتأخر، القادم، المفتوح والمكتمل. الإكمال يحتفظ بالصف ويضيف نشاطًا واحدًا؛ إعادة نفس الطلب لا تكرر المهمة. لا توجد متابعة آلية حسب نص رسالة أو حدث خارجي.
7. **البيع/الإيجار والمدفوعات:** متوقف على فحص المصدر والتأكيد التجاري أدناه. حالة العميلة لا تُنشئ transaction ولا تثبت تحويلًا أو تحصيلًا. لا تختزلي عدة عمليات في notes ثم تعتبريها دفتر مدفوعات.
8. **التسليم/الإرجاع والإغلاق:** غير آلي وغير منفذ كدورة مالية/مخزون لغياب قواعد مؤكدة. يمكن إدارة المهام والمواعيد بأسماء مضبوطة لذلك، لكن هذا لا يغلق عقدًا أو يثبت عودة فستان.
9. **الرحلة والنشاط:** الملف يجمع المواعيد والمهام والنشاط المرتبط بمعرّفات السجلات، وليس بالاسم. تغيير الاسم لا يكسر العلاقات. لا تتم إعادة كتابة أسماء تاريخية مخزنة في زيارات سابقة تلقائيًا.

## القوائم ومصدرها

تبويب «القوائم المنسدلة» يحتوي: المصادر، حالات العميلات، الخدمات، الموديلات، الموظفات، أنواع المواعيد، حالات المواعيد، حالات المتابعات. كل قائمة عمود مستقل من الصف الثاني. لا تضعي blanks وسط الخيارات، وتجنبي التكرار. لا يحذف script قيم القائمة الموجودة أو يعيد ترتيبها.

- أول تجهيز يستخرج القيم الموجودة من الجداول المتوافقة، ويجمع أسماء الموظفات الموجودة في العملاء/المواعيد/المتابعات.
- إذا كانت الجداول فارغة، القيم الموروثة الوحيدة من المصدر هي: عميلة «جديدة»، موعد «مؤكد/ملغي» ونوع «زيارة»، ومتابعة «جديدة/مكتملة». لا تُخترع أسماء أو خدمات أو مصادر أو dress codes.
- إذا كانت vocabularies الفعلية غير مطابقة، تُترك mappings المناسبة في «إعدادات النظام» فارغة كي تراجعيها. لا يتم ترجمة المعنى التاريخي أو توحيده تلقائيًا.
- الإعدادات: `customerNew`, `appointmentConfirmed`, `appointmentCancelled`, `taskOpen`, `taskComplete`, `appointmentDefaultType`, `allowedEmails`.
- Named Ranges: `RB_SOURCE`, `RB_CUSTOMER_STATUS`, `RB_SERVICE`, `RB_MODEL`, `RB_STAFF`, `RB_APPOINTMENT_TYPE`, `RB_APPOINTMENT_STATUS`, `RB_TASK_STATUS`.
- بعد تغيير القوائم: نسخة احتياطية حديثة → تحديث القوائم من القائمة. الأسماء الحالية لا تُستبدل إذا كانت تشير لغرض آخر.
- Named Range المتاح يُطبَّق على كامل الصفوف الموجودة والفارغة الحالية. عند توسيع حجم الشيت يدويًا، راجعي استمرار القواعد وشغّلي تحديث القوائم بعد النسخ الاحتياطي. ليس هناك onEdit trigger يغيّر البيانات أو ينسّق الصفوف تلقائيًا.
- Dropdowns تسمح ببقاء قيمة تاريخية مع تحذير؛ API يسمح ببقائها عند عدم تغييرها ويرفض قيمة جديدة خارج القائمة المهيأة. القوائم غير المهيأة لا تتحول إلى ادعاء وجود validation؛ تُسجّل في `missingLists` وتحتاج إعدادًا.

## لوحة الإدارة والتعريفات

مصدر كل قيمة هو الجداول الحالية. حساب اليوم حسب Africa/Cairo؛ التواريخ غير القابلة للفهم لا تدخل تقارير المواعيد/الاستحقاق ويظهر عددها كتحذير. تحوي اللوحة:

- إجمالي صفوف العميلات غير الفارغة (يشمل التاريخي بلا ID مع تحذير).
- الاستفسارات بالحالة المحددة في customerNew **حاليًا**؛ ليست عدد الاستفسارات الواردة في فترة ولا تعويضًا عن سجل تاريخ الحالة.
- مواعيد اليوم ومواعيد الأيام التالية، باستثناء appointmentCancelled. مواعيد اليوم تقارن التاريخ لا الساعات المنقضية.
- المهام المفتوحة، اليوم، المتأخرة، المكتملة بحسب taskComplete؛ المستقبل لا يدخل المتأخر.
- توزيع العميلات حسب المصدر والحالة، من القيم الفعلية، دون اختلاق تحويلات أو إيرادات.

تُحدّث اللوحة بعد كل كتابة ناجحة. إذا فشل تحديث مشتق، يظل السجل محفوظًا وتعود رسالة تحذير؛ استخدمي تحديث لوحة الإدارة. التعديلات اليدوية المباشرة تحتاج refresh؛ لا توجد إعلانات تلقائية عن تحديث لحظي. لا توجد conversion rate أو revenue أو balances لغياب مقامات/فترة/معاملات مؤكدة.

## معلومات لازمة قبل الجزء المالي

يحتاج المستخدم تأكيد: هل البيع والإيجار مسجلان في تبويبات مستقلة؟ ما المعرفات والعملة وطريقة تسجيل الأقساط؟ هل الخصم جزء من المبلغ المتفق عليه أم adjustment؟ كيف تُسجّل refunds والإلغاء؟ ما مدد الحجز والاستلام والإرجاع وشروط إقفال عقد وتأخير/تلف؟ هل الفستان له وحدة فريدة أم عدة قطع؟

إلى أن تتضح هذه القواعد، **لم تُنشأ** تبويبات مبيعات أو مدفوعات أو مخزون، ولم تُحتسب إيرادات أو أرصدة. التصميم المقترح بعد الموافقة: Transaction ID يربط Customer ID وDress ID، وPayment ID منفصل لكل قسط مرتبط بمعاملة، ورصيد يساوي المبلغ النهائي ناقص المدفوعات الموثقة وفق قواعد adjustments/refunds المعتمدة. هذا اقتراح نموذج، وليس تنفيذًا أو تاريخًا ماليًا موجودًا.
