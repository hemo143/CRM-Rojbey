# التركيب والتفويض والتحقق الحي

## 1. الحصول على المصدر الحقيقي

الرابط المرسل يخص Spreadsheet واحدًا؛ تغيّر `gid` يختار تبويبًا آخر ولا يغيّر الملف. لم تنجح قراءته من بيئة Codex: رُفض CONNECT إلى `docs.google.com` برمز 403 قبل الوصول إلى Google. لم تُجرّب صلاحية حساب المستخدم لأن البيئة لا تعرض حساب Google مفوّضًا لهذا الشيت. إضافة الرابط في المحادثة لا تمنح تلقائيًا OAuth.

تم حفظ إضافة `docs.google.com` في مسودة إعدادات البيئة فقط؛ لا يُدّعى أنها طُبّقت. يمكن مراجعتها وحفظها في إعدادات البيئة عند الرغبة في إعادة محاولة القراءة. لا تجعلي بيانات العملاء عامة. تم بالفعل فحص XLSX المرفق؛ راجع WORKBOOK_AUDIT.md. لا حاجة لإعادة رفعه. هذا لا يمنح تفويضًا للشيت الحي.

يلزم فحص كل التبويبات والأعمدة والصيغ والقوائم وNamed Ranges ونوع الهاتف والتواريخ وvocabularies، والحصول على أحدث مصدر Apps Script الفعلي. الكود الحالي مبني على المصدر المتاح؛ ليس تصريحًا باستبدال مشروع حي أحدث.

## 2. نسخة اختبار ومشروع مرتبط

1. من الشيت الأصلي: File → Make a copy لإنشاء ملف اختبار خاص؛ لا تشغلي اختبارات الإضافة أو تعديل المخطط على بيانات الإنتاج.
2. صدّري مصدر Apps Script القديم، HTML وmanifest وكل الملفات، واحفظيها في مكان خاص خارج المستودع إذا تضمنت معلومات حساسة.
3. من نسخة الاختبار افتحي Extensions → Apps Script. افحصي هل نُسخ المشروع المرتبط وإعداداته. لا تشغلي أي قائمة قديمة قبل مراجعة Spreadsheet binding.
4. في **مشروع الاختبار فقط**: استبدلي محتوى Code.gs بالنسخة الجديدة وأضيفي Schema.gs وSetup.gs وWorkbook.gs وIndex.html؛ اعرضي `appsscript.json` من Project Settings وضعي manifest المرفق. تجنبي ترك الثوابت والدوال القديمة مكررة بجانب الملفات الجديدة.
5. لا تضعي tokens أو كلمات مرور أو معلومات عميلات داخل المصدر. لا حاجة لـMeta credentials.

## 3. التفويض والربط والتدقيق

شغّلي `RB_bindSpreadsheet` من محرر المشروع المرتبط. يحفظ Spreadsheet ID ومديرة الإعداد في Script Properties فقط. يرفض تبديل الربط إلى ملف آخر أو تغيير المديرة من حساب مختلف. إذا نُسخت Properties من المشروع الأصلي، توقفي: راجعي Script Properties للنسخة مع المسؤول ولا تتجاوزي الحماية على مشروع الإنتاج.

وافقي في شاشة Google على الصلاحيات بعد مراجعة المصدر:

- `spreadsheets`: قراءة/كتابة الشيت المستهدف، إنشاء نسخة احتياطية وفتحها للتحقق.
- `script.container.ui`: Sidebar وقائمة CRM داخل الشيت.
- `userinfo.email`: تحديد المستخدم والتحقق من السماح.
- `script.scriptapp`: جرد triggers التي يراها حسابك؛ المصدر لا ينشئ triggers.

لنسخة الملف المفحوصة شغّلي `RB_configureObservedWorkbook` بعد الربط وقبل التدقيق. يتحقق من العناوين ويضبط Properties فقط دون تعديل الخلايا، لإعادة استخدام «القوائم والإعدادات». إذا رفض المخطط لا تتجاوزي الرفض.

شغّلي `RB_showAudit` من القائمة بعد تحديث صفحة Sheets، أو `RB_audit` من المحرر. التقرير لا يحتوي قيم عميلات، ويعرض headers والأنواع وأعداد الصيغ/validation وNamed Ranges وtriggers. لا تسجلي نتائج الدالة الخام المحتوية على بيانات العملاء في console. نتائج RB_audit هي metadata فقط؛ يمكن مشاركتها للفحص بعد مراجعتها.

إذا وجد تبويب مكافئ باسم آخر، راجعي مخططه ثم اضبطي Script Property `RB_SHEET_MAP` كـJSON، مثال **للتوضيح فقط**: `{"customers":"Customers"}`. لا تعيدي تسمية تبويبات أو أعمدة إنتاجية تلقائيًا. أسماء الأعمدة الأصلية مطلوبة؛ عدم التطابق يحتاج خريطة ترحيل منفصلة ونسخة احتياطية وموافقة واضحة. لا تستخدمي rename لتجاوز الرفض قبل فهم البيانات.

## 4. النسخ الاحتياطي والتجهيز على نسخة الاختبار

1. أوقفي التعديل المتزامن مؤقتًا.
2. شغّلي `RB_createBackup`. افحصي `verified:true` وافتحي النسخة الناتجة بحسابك؛ لا تعتمدي على الاسم فقط.
3. شغّلي `RB_setup`. إضافة headers داخلية/تبويبات إعدادات لا تبدأ على ملف غير فارغ دون نسخة مطابقة للحالة الحالية.
4. راجعي `needsConfiguration`. إذا كانت الحالات الموجودة تختلف عن الكود القديم، تبقى بعض mappings فارغة؛ اختاري القيمة الصحيحة في «إعدادات النظام». لا يُعد ذلك اكتشافًا تلقائيًا لمعنى الحالة.
5. في الملف المفحوص تُستخدم «القوائم والإعدادات» الحالية. قائمة الموظفات الجديدة فارغة عمدًا واعتمادها مؤجل بطلب المستخدم؛ لا تعتمدي القيم التاريخية تلقائيًا. راجعي missingLists أيضًا. لا توجد أسماء أو كتالوج وهمي.
6. بعد تعديل القوائم، أنشئي نسخة احتياطية جديدة ثم شغّلي `RB_refreshValidation`. لا تعدّلي Named Ranges من مشاريع أخرى.
7. اختبري dropdown في صف موجود وصف فارغ فعليًا من واجهة Google Sheets. API يرفض الخيارات الجديدة غير الموجودة إذا كانت القائمة مهيأة؛ قواعد الشيت تسمح بظهور القيم التاريخية مع تحذير بدل حذفها.
8. شغّلي `RB_refreshDashboard` بعد إكمال mappings. لا تستبدلي أوراق dashboard قديمة غير متوافقة بهذا المخطط.

## 5. استخدام داخل Google Sheets

حدّثي صفحة الشيت لتظهر قائمة **ROJBEY CRM**، ثم **فتح CRM داخل الشيت**. Sidebar هو workflow داخل Sheets ويستخدم نفس مصدر Web App. يمكن للمديرة اعتماد صف عميلة تاريخي بلا ID بشكل صريح من القائمة؛ لا يتم إنشاء IDs لكل الصفوف القديمة كجزء من setup، ولا اختلاق تاريخ إضافتها.

عمليات التشغيل المعتمدة تتم من Sidebar/الواجهة كي تُولّد المعرفات ويُسجّل النشاط. اختيار Dropdown يدويًا أو لصق خلايا مباشرة لا يمر عبر هذا المسار، ولا تُدّعى له timestamps أو تدقيق أو حماية تزامن تلقائية. يمكن تنظيم صلاحيات Google للحماية من التعديل المباشر، لكن لا تُقفلي أعمدة يحتاج المستخدم المفوّض إلى كتابتها عبر script يعمل بهويته قبل الاختبار.

## 6. Web App

Deploy → New deployment → Web app. اختاري التنفيذ **User accessing the web app**، وابدئي بأضيق وصول متاح لحساب الاختبار. أضيفي بريد كل موظفة مسموحة في إعداد `allowedEmails` بعد التأكد من وجود صلاحية Google Sheets اللازمة لها. المديرة التي أجرت الربط مسموحة تلقائيًا.

أكملي تفويض كل حساب عند اللزوم. إذا لم يرجع Google بريد المستخدم، يفشل النظام مغلقًا؛ لا تبدلي إلى تشغيل عام بهوية المالك لتجاوز المشكلة. وصول الحسابات الشخصية/مراجعة OAuth قد يختلف عن Workspace ويحتاج تأكيدًا في حساب Google الفعلي. لا نعتبر هذا النشر منجزًا محليًا.

اختبري رابط النشر، القراءة، إضافة سجل اختبار، إعادة تحميل الصفحة، ثم افتحي الشيت نفسه وتحققي من نفس ID والقيم. اختبري تعديل السجل، موعدًا ومتابعة، dropdowns، الصلاحيات، والعمل من حسابين. سجّلي النتائج في TEST_REPORT. بعد اجتياز نسخة الاختبار، راجعي التدقيق والنسخ الاحتياطي والموافقة قبل أي تغييرات بمخطط الإنتاج. احتفظي بالـdeployment/version السابق للرجوع.
